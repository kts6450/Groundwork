## 2026-09-14 저장·홍보물·업종 분포로 1~7단계 마감

### 프로젝트 저장을 SQLite로 먼저 만든 이유

5단계는 "저장된 프로젝트를 새 시점으로 다시 계산"하는 것이라 저장소 없이는 반쪽이었다.
Supabase는 키가 있어야 하므로, 같은 함수 시그니처를 가진 SQLite 구현을 먼저 뒀다.
`src/projects/store.py`의 save/get/list/delete만 지키면 Supabase로 갈아끼울 때 바깥 코드는 안 바뀐다.
로그인이 없어 `user_id`는 호출자가 넘기는 문자열이다.

### 업종 분포는 절대 수가 아니라 전국 대비 배수

원래 기획의 '업종 분포도'다. 지도 키가 없어 지도 대신 막대로 만들었다.
절대 수로 그리면 인구가 많은 구는 모든 업종이 많아 어디나 비슷해 보인다.
전국 구성비와 비교한 `ratio`라야 "여기는 유독 일식이 많다"가 드러난다.

- 표본 5곳 미만 업종은 headline에서 뺀다. 3곳짜리 업종이 10배로 나오면 오해를 부른다
- 실데이터: 마포구 일식 2.70배, 종로구 양식 2.65배. 실제 상권 인상과 맞는다

### 홍보물(7-2)도 같은 폴백 구조

저장된 이름·팔레트·톤을 프롬프트에 넣어 매번 같은 브랜드로 보이게 한다.
프롬프트에 "없는 할인율·수상 이력·원산지를 지어내지 말라"를 명시했다. 가게가 실제로 쓸 문구이고
거짓이 들어가면 사용자가 책임을 진다.

### 남은 것은 전부 사람 손이 필요하다

`ANTHROPIC_API_KEY`(LLM 경로 실제 확인), Kakao 지도 키, Supabase, 행정동 경계 파일, 상표 확인.
코드로 더 나아갈 수 있는 부분은 없다.

## 2026-09-13 2·3·5단계 구현 (LLM 경로는 키 없이도 도는 구조)

### 생성 단계의 공통 뼈대

2단계(컨셉·메뉴)와 3단계(브랜드명·로고)를 같은 구조로 만들었다.
`schema → prompts → generate(LLM 시도 → 검증 → 실패 시 mock)`.

- **키가 없어도 전부 동작한다.** `ANTHROPIC_API_KEY`가 없거나, 호출이 실패하거나,
  결과가 형식을 어기면 규칙 기반 목업으로 내려간다. `source` 필드가 어느 쪽인지 밝힌다
- 이유: 시연 중 외부 장애로 화면이 비면 안 되고, 키 없이 테스트가 돌아야 한다(CLAUDE.md 규칙)
- 모델은 `claude-opus-5`, structured outputs(`output_config.format`)로 JSON을 강제

### 근거 숫자는 모델이 아니라 코드가 채운다

`grounds`(생존률·표본 수·판정)는 LLM 응답을 쓰지 않고 검증 결과에서 코드가 만든다.
모델이 통계를 지어내는 순간 "근거 있는 기획"이라는 차별점이 무너지기 때문이다.
테스트로 고정했다(`test_generate_overwrites_grounds_the_model_invented`).

같은 이유로 브랜드 이름의 `risk`는 모델이 뭐라 쓰든 "상표는 사람이 직접 확인해야 한다"로 덮는다.

### LLM이 만든 SVG는 살균한다

로고를 SVG 문자열로 받아 화면에서 `dangerouslySetInnerHTML`로 렌더하므로,
`script`·`on*` 속성·외부 이미지·`javascript:` URL이 들어오면 그대로 실행된다.
`src/branding/svg.py`가 허용 목록 방식으로 걸러낸다. 모르는 태그·속성은 통과 못 한다.
고정 `width`/`height`도 제거한다(레이아웃을 깬다). 32KB 상한.

### 5단계: 생존률이 아니라 개·폐업 수로 답한다

생존표는 고정 코호트(2015~2023)로 계산한 값이라 확인 시점에 따라 바뀌지 않는다.
시점에 따라 바뀌는 것은 **주변 점포 수**이므로, 상권 변화는 월별 개·폐업 집계로 답한다.

- 시군구 × 업종 × 연월 집계표를 미리 만든다(404,151행). 매 요청마다 290만 행을 훑지 않기 위해
- **기준선 행**: 집계 시작(2010-01) 이전에 열어 그때까지 살아 있던 점포 수를 `month="0000-00"` 행에 담는다.
  이게 없으면 옛 점포의 폐업만 잡혀 영업 중 점포 수가 음수가 된다(종로구 한식 -151곳이 나왔다).
  `0000-00`은 어떤 실제 연월보다 작아 구간 조회에는 안 잡히고 누적 조회에는 항상 잡힌다
- 프로젝트 저장(Supabase)이 없으므로 위치·업종·시점을 요청으로 직접 받는다

### 화면

검증 결과가 나오면 "이 자리로 기획안 만들기" 버튼이 뜨고 `/backend/plan`이 1~3단계를 한 번에 준다.
목업으로 만든 결과는 화면에서 규칙 기반임을 밝힌다. 숨기면 사용자가 시세 정보로 오해한다.

## 2026-09-13 3주 차: 검증기 동작, 백테스트, 업태 폐지 문제

### 발견: 인허가 업태 코드는 중간에 폐지된다

`통닭(치킨)` 업태는 2016년경 신규 등록이 끊겼다(2021~23년 1건). 치킨 묶음이 이 업태만 담고 있어서
사실상 2015년 개업분 1,221곳으로 3년 생존률을 내고 있었다. 상호로 확인해 보니 치킨집의 71%가
`호프/통닭`으로 등록하고, 호프/통닭의 40%가 치킨 상호다. 업태만으로는 둘을 가를 수 없다.

- **치킨 + 호프/통닭 → '치킨·호프'** 한 묶음. 주점은 정종/대포집·감성주점·라이브카페만 남김
- **'베이커리·디저트' → '디저트'.** 과자점 업태도 폐지됐고(2021~23년 0건), 빵집 상호는
  기타 휴게음식점·커피숍·일반조리판매로 흩어져 업태로 식별 불가. 이름에서 '베이커리'를 뺌
- **`audit.py` 추가.** 매 실행마다 폐지 업태와 영향받는 묶음 비율을 검출해 보고서에 경고.
  같은 함정을 다음에 또 밟지 않으려고 사람 눈이 아니라 코드로 막았다

### 백테스트 (이 프로젝트를 '분석'에서 '모델'로 만드는 부분)

- 학습 2015~2019 개업 445,256곳 → 생존표. 평가 2020~2022 개업 286,800곳 → 예측 후 실제와 비교
- 평가 코호트의 폐업은 표에 넣지 않는다. 테스트로 고정(`test_run_backtest_does_not_leak_test_closures_into_tables`)
- AUC: 전체평균 0.500 → 업종만 0.546 → 업종+지역 0.570
- **등급별 실제 3년 생존: 합격 70.1%, 주의 63.1%, 위험 59.6%. 격차 10.6%p**
- AUC가 낮아 보여도 등급 격차가 크면 쓸모가 있다. 개별 점포의 운명은 상권보다 운영이 좌우하기 때문
- 평가 기간이 코로나와 겹친다는 한계를 보고서에 명시

### 검증기에 근거를 붙임

"합격"이라고만 말하지 않고, `evidence.py`가 "같은 판정을 받은 73,055곳의 3년 생존은 70.1%였다"를
함께 반환한다. 숫자는 `run_backtest`가 JSON으로 내보내고 검증기가 읽는다. 손으로 고치지 않는다.

### 스택 앞당김

FastAPI·Next.js를 8주차 예정에서 3주 차로 당겼다. 검증기가 동작하는 걸 화면으로 봐야 다음 단계
판단이 서기 때문. 지도(Kakao)와 Supabase는 아직 넣지 않았다.

### 작업 환경에서 배운 것

- Cursor와 Claude Code를 오가며 `uvicorn`·`next dev`를 여러 번 띄워 좀비 프로세스가 포트를 잡고
  옛 코드를 응답했다. 포트가 잡혀 있으면 `Get-NetTCPConnection`으로 실제 살아있는지 먼저 확인할 것
- `npm run build`는 실행 중인 dev 서버의 `.next`를 깨뜨린다. 빌드 검증 후에는 dev를 재시작한다

## 2026-09-11 기획 방향 확정 (1인 개발 시작)

### 출발점 (원래 아이디어, 사용자 표현 그대로)

> 자영업을 시작하려는 사람들, 즉 음식점·카페 창업을 하려는데 메뉴·로고 등 아무것도 정하지 않은 사람 대상으로 이런 것들을 생성해주는 것.
> 어느 분야로 할지, 무슨 메뉴, 로고, 심지어 어느 부지·어느 건물에 입점하는 게 좋다까지. 업종 분포도도 보여주고. 브랜딩 시각화 느낌.

원래 아이디어에서 초안으로 옮기며 좁아진 두 가지:
- "어느 건물"이 "행정동"으로 내려왔다. 공실·매물 데이터가 없어 건물 단위 추천은 확신 있게 못 한다. 상가정보의 건물관리번호로 "동종이 몰린 건물"까지는 가능 → 로드맵
- "브랜딩 시각화"가 로고 하나로 줄었다. 5단계 브랜드 자산 생성으로 다시 넓힘

### 결정 1. 파이프라인을 4단계 → 5단계로 확장 (개업 이후)

- **문제**: 기존 4단계는 "입력 → 기획안"으로 끝나는 일회성 구조. 창업 후 앱을 다시 쓸 이유가 없음
- **검토한 대안**
  - A. 상권 모니터링: 개업 시점 점수를 새 시점으로 재계산해 "반경 내 동종 개업 N, 폐업 M" 알림
  - B. 브랜드 자산 계속 생성: 저장된 브랜드 정체성으로 시즌 메뉴 포스터·SNS 게시물 등 생성
  - C. 폐업 위험 진단: A + 사용자 매출 입력으로 생존 확률 갱신
- **결정**: A + B를 5단계로 채택. C는 로드맵
- **이유**: A는 1단계 코드·데이터를 그대로 재사용하므로 추가 비용이 가장 낮고, 일회성 점수가 시계열이 되는 순간 제품 성격이 바뀜. B는 A 위에 얹는 확장. C는 사용자가 매출을 직접 입력해야 해서 이탈 지점이 생기고 POS 연동은 범위를 넘음

### 결정 2. 차별점은 "생존률"

- **문제**: 상권 지표가 밀집도+인구 정도이고 뒤 단계가 프롬프트면 "공공데이터 시각화에 LLM 붙인 것"으로 보임
- **결정**: 인허가 개·폐업 이력으로 "이 동에서 이 업종의 N년 생존률"을 계산하고, 과거 시점으로 돌아가 예측이 맞았는지 백테스트한다
- **이유**: 기존 상권분석 서비스는 "지금 얼마나 팔리나"를 전면에 내세운다(docs/market.md). 생존률은 그들이 안 하는 메시지이고, 백테스트 하나가 프로젝트를 "분석"에서 "모델"로 바꿈

### 결정 3. 시점 필터를 공통 기반으로

- 인허가일자·폐업일자로 "시점 T에 영업 중이던 점포"를 날짜 필터 한 줄로 재구성 가능
- 이 하나로 백테스트(과거 시점 점수 vs 이후 폐업)와 5단계 모니터링(두 시점 점수 차이)이 모두 해결됨
- 매달 데이터를 새로 받지 않고 파일 하나로 시연 가능 → 1인 개발에서 5단계가 현실적인 이유

### 결정 4. SaaS 구조로 설계, 스택은 얇게

- **문제**: "SaaS로 만든다"에 두 가지가 섞여 있었음. (1) 회원·프로젝트 저장·시간에 따른 재계산이라는 제품 구조, (2) React+API+인증+결제+배포라는 기술 스택
- **결정**: (1)은 처음부터 설계에 넣는다(사용자 프로젝트 객체). (2)는 혼자 감당할 수 있는 최소로 시작하고 층별로 갈아끼울 수 있게 한다
- **핵심 원칙**: 분석·생성 로직은 `src/`에 두고 화면·API를 모른다. FastAPI는 감싸기만, 프론트를 바꿔도 로직은 안 바뀜

### 결정 5. 화면 스택: Streamlit 불채택 → Next.js + FastAPI

- **처음 제안**: Streamlit 단일 앱 (프론트·백엔드 분리 없이 가장 빠름)
- **사용자 판단**: Streamlit은 별로 → 불채택
- **검토한 대안**
  - A. Next.js + FastAPI. 파이썬 로직을 FastAPI가 그대로 감싸고, 프론트는 별도 앱
  - B. Next.js 단독 + 파이썬은 배치. 점수를 미리 다 계산해 DB에 넣고 Next.js가 읽기만
  - C. Django 풀스택. 파이썬 한 언어, 인증·관리자 포함
- **결정**: A
- **이유**: 5단계에서 저장된 프로젝트를 다시 계산하는 로직은 파이썬 서비스로 살아 있어야 자연스럽다. B는 미리 계산이라 사용자 조건 실시간 반영이 약하고, C는 지도·차트에서 결국 JS를 따로 쓰게 되어 화면 완성도에서 손해
- **혼자 하는 부담 줄이기**: 처음엔 FastAPI 엔드포인트 하나에 파이프라인 전체, 프론트는 화면 2장(입력·결과)으로 9주차 데모. 로그인·저장은 Supabase에 맡겨 10주차에
